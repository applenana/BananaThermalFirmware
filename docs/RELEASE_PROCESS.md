# 发布与版本策略

## 版本号

正式固件采用 SemVer 风格的版本号：

```text
v1.6.0
v1.6.1
```

- 主版本：存在需要明确迁移的重大变化；
- 次版本：新增能力或较大范围改进；
- 修订版本：兼容性修复、稳定性修复或小幅优化。

当前自动发布通道只接受 `v主版本.次版本.修订号` 形式的正式版本；预览构建不进入正式固件分发列表。

自动分发从 `v1.7.0` 开始。更早的内部版本不会由本仓库补发；最低版本可通过发布仓库的 `MINIMUM_FIRMWARE_TAG` 变量提高，但不能用它发布不符合正式版本格式的 Tag。

## Release 是唯一下载入口

正式固件只通过本仓库的 Releases 分发。不要从聊天附件、网盘转载、构建日志或来源不明的镜像下载固件。

一个版本只有同时满足以下条件才视为完整：

1. Release 已正式发布且不是 Draft；
2. v1.7.x 包含三个历史 UF2；v1.8.0 起包含六个 dual / standard UF2；
3. 包含 `manifest.json`、`SHA256SUMS` 和签名；
4. 签名能够由仓库中的公开签名身份验证；
5. Release 附件启用了不可变保护。

只有同名 Git Tag、但没有完整 Release 附件的版本，不应安装。

## 自动构建

发布系统按小时检查官方受控版本。发现尚未发布的版本后，会从精确 Tag 按单一发布矩阵构建环境：v1.7.x 使用 schema v1 三环境，v1.8.0 起使用 schema v2 六环境。

每次最多处理一个版本，避免网络恢复或版本积压时同时启动大量构建。定时任务不是实时系统，可能出现延迟；维护者可以使用相同规则手动补发。

手动入口另提供 `check_only` 安全诊断模式。启用后只验证配置、版本可见性和 Release 状态，不会抓取源码、编译、签名或创建 Release。

## 发布事务

1. 选择精确版本 Tag；
2. 将 Tag 注入为固件的编译期 `FIRMWARE_VERSION`，并在干净的一次性环境中构建全部变体；
3. 通过扩展名与文件名白名单隔离 UF2；
4. 生成机器可读清单和 SHA-256；
5. 使用 Ed25519 发布密钥签名；
6. 创建 Draft Release 并上传附件；
7. 校验附件集合；
8. 发布正式 Release；
9. 由 GitHub Release immutability 锁定。

任意变体构建失败、附件缺失或签名验证失败都会阻止发布。

发布流程会在构建二进制中核对版本、型号、板型和完整环境名。dual 必须包含 `HEIMAN-NSP-<Tag>-32`，standard 必须包含 `HEIMAN-NSP-STANDARD-<Tag>-32`；v1.8.0 起还必须包含对应 `BANANA-THERMAL:<板型>:<环境>` 身份。

## 更新说明

维护者可在 `docs/releases/<Tag>.md` 中提前准备正式说明；文件存在时，发布流程会原样使用它作为 Release Notes，否则使用安全的通用说明。

每个正式版本应说明：

- 新增功能；
- 修复问题；
- 兼容性变化；
- 是否需要重置配置或迁移文件系统；
- 已知问题；
- 建议使用的上位机最低版本。

固件升级前应先阅读对应 Release Notes，而不是仅根据“最新版”判断是否适合当前设备。

## v1.8.0 上线顺序

统一固件首次上线固定按以下顺序执行：先发布支持旧设备迁移和 schema v2 的新版 NextBananaThermalStudio，再合入并启用本分发系统，随后创建固件 v1.8.0 Tag/Release，最后完成普通热成像 Heimann/MLX 与 2 MB/8 MB 真机迁移验证。不得在新版 Studio 可用前发布 v1.8.0 固件。
