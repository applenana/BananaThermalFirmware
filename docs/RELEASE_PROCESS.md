# 发布与版本策略

## 版本号

正式固件采用 SemVer 风格的版本号：

```text
v1.6.0
v1.6.1
```

- 主版本：存在需要明确迁移的重大变化；
- 次版本：新增能力或较大范围改进；
- 修订版本：兼容性修复、稳定性修复或小幅优化。

当前自动发布通道只接受 `v主版本.次版本.修订号` 形式的正式版本；预览构建不进入正式固件分发列表。

自动分发从 `v1.7.0` 开始。更早的内部版本不会由本仓库补发；最低版本可通过发布仓库的 `MINIMUM_FIRMWARE_TAG` 变量提高，但不能用它发布不符合正式版本格式的 Tag。

## Release 是唯一下载入口

正式固件只通过本仓库的 Releases 分发。不要从聊天附件、网盘转载、构建日志或来源不明的镜像下载固件。

一个版本只有同时满足以下条件才视为完整：

1. Release 已正式发布且不是 Draft；
2. 包含三个 UF2 变体；
3. 包含 `manifest.json`、`SHA256SUMS` 和签名；
4. 签名能够由仓库中的公开签名身份验证；
5. Release 附件启用了不可变保护。

只有同名 Git Tag、但没有完整 Release 附件的版本，不应安装。

## 自动构建

发布系统按小时检查官方受控版本。发现尚未发布的版本后，会从精确的版本 Tag 构建三个 PlatformIO 环境，完成哈希与签名验证后发布。

每次最多处理一个版本，避免网络恢复或版本积压时同时启动大量构建。定时任务不是实时系统，可能出现延迟；维护者可以使用相同规则手动补发。

## 发布事务

1. 选择精确版本 Tag；
2. 将 Tag 注入为固件的编译期 `FIRMWARE_VERSION`，并在干净的一次性环境中构建全部变体；
3. 通过扩展名与文件名白名单隔离 UF2；
4. 生成机器可读清单和 SHA-256；
5. 使用 Ed25519 发布密钥签名；
6. 创建 Draft Release 并上传附件；
7. 校验附件集合；
8. 发布正式 Release；
9. 由 GitHub Release immutability 锁定。

任意变体构建失败、附件缺失或签名验证失败都会阻止发布。

发布流程还会扫描每个 UF2 中的兼容版本字符串，确认其包含 `HEIMAN-NSP-<Tag>-32`。因此即使构建成功，只要固件内版本与 Release Tag 不一致也不会发布。

## 更新说明

维护者可在 `docs/releases/<Tag>.md` 中提前准备正式说明；文件存在时，发布流程会原样使用它作为 Release Notes，否则使用安全的通用说明。

每个正式版本应说明：

- 新增功能；
- 修复问题；
- 兼容性变化；
- 是否需要重置配置或迁移文件系统；
- 已知问题；
- 建议使用的上位机最低版本。

固件升级前应先阅读对应 Release Notes，而不是仅根据“最新版”判断是否适合当前设备。
